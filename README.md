# abp_conference

## Контекст задачі:
Ви працюєте в компанії, яка розробляє застосунок для управління бронюванням та 
орендою конференц-залів. Ваше завдання — створити API для управління залами, 
бронюваннями та розрахунку вартості оренди.

## Опис проблеми:
Компанія надає в оренду конференц-зали для бізнесу. Необхідно розробити просте 
API, яке дозволить клієнтам шукати доступні зали, бронювати їх, а також 
розраховувати вартість оренди залежно від часу та обраних послуг.

## Рішення
### Архітектура
для реалізації створено дві моделі: Зал (Hall)
та Бронювання (Reservation), 
які представляють відповідні таблиці з БД

Інформація про зал: Id, Name, Capacity, Services, BasePrice

Інформація про бронювання: Id, HallId, BeginTime, EndTime, Active, Services, TotalPrice (BaseFee + ServiceFee), Hall

#### Збереження даних про доступні сервіси
Мною розглянуто три варіанти збереження інформації про сервіси в БД:
- Окрема таблиця. Така таблиця зберігатиме наступні дані про кожен сервіс: ID, Назва, Ціна
Оскільки один зал може містити декілька сервісів, потрібна також зв'язуюча таблиця зал-сервіс 
- Бітові маски:
Цей підхід використано при практичній реалізації для фільтрації фільмів за жанрами ([під час виробничої практики](https://github.com/vjwua/cnu_cinema_practice) та у [демонстрації](https://viacheslav-rudyi.github.io/binary-genre-filter/) )
Інформація зберігається єдиним unsigned цілим числом, де кожен біт відповідає за певну послугу. Наприклад:

| 0   | 0   | 1   | 0   | 0     | 1                        | 0    | 0        |
| --- | --- | --- | --- | ----- | ------------------------ | ---- | -------- |
| ... | ... | ... | ... | wi-fi | додаткове <br>освітлення | звук | проєктор |


Переваги:
1.  Зменшення використаної пам'яті
2. Швидкодія і спрощення запитів: відсутні одночасні запити до кількох таблиць, прості бінарні операції для визначення кожного сервісу
Недоліки:
3. Сама бітова маска не зберігатиме інформації про ціну послуг(и)

- JSON-подібний запис
В такому разі інформація зберігається рядками, де назва і ціна послуги розділені двокрапкою. Самі послуги перелічені через кому. Наприклад:
wi-fi : 700,
проєктор : 1000

Кожен зал може мати унікальні послуги. Інформація про назву і ціну зберігається в одному місці. При масштабуванні стандартні послуги можна вивести в окрему таблицю, подібно до першого варіанту. Однак запит до цієї таблиці потрібен тільки для отримання або модифікації списку послуг, а не при отриманні інформації про кожен зал

Для реалізації задачі було обрано останню опцію. Реалізовано допоміжні функції для зручнішої роботи з текстами сервісів: отримання назви, отримання ціни, переведення у Dictionary та навпаки, валідація коректності запису

___!!! Вибір цього варіанту презюмує, що ціна на одну послугу може різнитис яміж залами. Наприклад, проєктор в Залі А коштує 500грн/год, а проєктор в Залі Б -- 700грн/год.  
Якщо ціна послуги ідентична між усіма залами, абсолютну перевагу має варіант з бітовими масками___

### API
__Для тестування API підключено інтерфейс Swagger__
реалізацію API поділено на два контролера: HallsController і ReservationsController.

HallsController: 
1. створення залів, 
2. редагування інформації про них, 
3. отримання списку залів,
4. видалення

ReservationsController: 
1. перегляд доступних залів у відповідний часовий проміжок з обмеженням мінімальної місткості залу
2. створення нового бронювання у відповідний час та тривалість. Неможливо створювати бронювання в період 23:00 - 06:00. Не передбачено можливість бронювання на кількаденний період за раз. Для замовлення додаткових послуг їх найменування необхідно перелічити через кому [при подальшій розробці користувацького інтерфейсу необхідність прописувати їх буде відсутня. Натомість, вже реалізовані функції приведення інформації про послуги у форму словника дозволять легко вивести їх в окремий список/форму]
3. перегляд та видалення бронювань

## Аналітика
Таке рішення має для бізнесу наступні переваги:
1. Автоматизація перевірок на конфлікти у графіку бронювань
2. Збереження даних, доступних для подальшої аналітики (наприклад, визначення трендів у годинах і залах бронювання, кількості відвідувачів)
3. Автоматичний розрахунок оренди враховує весь перелік послуг, знижки/додаткові націнки
4. Створений API може бути основою для подальшої розробки сайту/сервісу для бізнесу з метою спрощення процесу бронювання для клієнтів та кращої впізнаваності компанії
